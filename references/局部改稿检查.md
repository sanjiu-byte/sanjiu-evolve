# 局部改稿的可执行检查（给 AI）

用于已有脚本、提示词或其他纯文本的局部修改。目标是让“只改这里”落到实际成品上，同时保留情绪、意思与其他当前要求。工具不会判断哪个要求正确，也不会自动找到所有遗漏。

## 何时执行

本轮修改范围可以定位到原稿中的若干片段，且环境能读写本机文件、运行 Python 3.9+ 时，由你执行下面流程，不让员工学习命令、填写 JSON 或逐项确认已经明确的信息。不需要第三方库、联网或额外模型 API。

新写稿、明确全文重构时沿用普通创作流程；不要硬把全文包装成“局部修改”。只提供一个 MD 的聊天环境没有运行能力，要说明未运行程序，并人工对照改变项和保留项。缺 Python 时先用现有可用解释器；确实没有则退回文字检查，不自行下载整套开发环境。

用户说本轮“不记”时，不为这条反馈新建要求文件、快照、检查日志或任务记录，直接在当前上下文对照修改；如实说明没有运行这项落盘检查。不能把“不记”改名为审计留存。

## 1. 核对当前依据，准备本地输入

先读当前基线、匹配任务记录和权威要求正文，判断本轮改变项与保留项。不要把上次助手摘要视为权威；后来的用户明确改向优先。基线可为工作稿，但注明状态，不能称为客户已确认稿。

选择已授权的、不入仓的本地位置，沿用现有项目记录目录。使用 `.local/sanjiu-evolve/` 前，先确认 Git 忽略且未跟踪；不满足就用已有的仓库外私有目录。真实输入和会话快照不得存进共享技能包。没有本地记录授权时使用文字检查，不从本文件取得额外权限。

保存四个 UTF-8 输入文件。以下均为虚构示例，路径为相对当前工作目录；实际基线沿用已有文件，不覆盖它。JSON 用序列化工具生成，避免手工转义引号和换行。

`baseline.txt`：

```text
【开头】她收到朋友递来的纸条。
【反应】她认出上面的字，眼眶一热，紧紧攥住纸条，轻声说：“你真的还记得。”
【结尾】两人相视而笑。
```

`request.txt` 是本轮用户原话，例如“只把反应那段写短一些，给我完整稿”。`requirements.json` 只放本轮仍有效的少量要求及可追溯来源：

```json
{"requirements":[
  {"id":"emotion","text":"保留认出字迹后的触动及可见表演。","source":"本项目当前要求：表演条款"},
  {"id":"ending","text":"结尾仍是两人相视而笑。","source":"当前基线与本轮局部修改范围"}
]}
```

`scope.json` 指定可以替换的原文，每段必须非空、在基线中只出现一次、彼此不重叠；不要包含不必修改的标题、时码和其他剧情：

```json
{"editable":[{"id":"reaction","text":"她认出上面的字，眼眶一热，紧紧攥住纸条，轻声说：“你真的还记得。”"}]}
```

实际 `text` 必须从基线**原样截取**，包括引号、空格与换行。重复句需用必要的相邻文字唯一定位，保留这些额外锚定文字。跨多处重复描述同一动作时，分别列出需要联动修改的片段。中文标点、BOM 和 CRLF 不应为方便定位而先整体格式化。

## 2. 冻结，再只写替换内容

将下面 `<技能目录>` 替换为实际安装路径；`python` 替换为本机可用解释器，每次用新的会话目录：

```text
python <技能目录>/scripts/edit_guard.py prepare --baseline baseline.txt --requirements requirements.json --request-file request.txt --scope scope.json --session edit-001
```

必须读取生成的 `edit-001/packet.md`，确认要求、请求、基线和范围匹配后，再写 `edits.json`。若理解后发现范围不对，回到用户需求修正并新建会话；不能为迎合已写好的新稿扩大范围。

```json
{"replacements":[{"id":"reaction","text":"她认出字迹，红着眼攥紧纸条：“你还记得。”"}]}
```

每个允许 ID 恰好出现一次；无需修改的片段填回原文，删除时用空字符串。此时就检查范围内的语义：精简是否保留触发、变化和可见表演；有没有把具体动作换成较弱的情绪标签，或改掉原因果。

```text
python <技能目录>/scripts/edit_guard.py render --session edit-001 --edits edits.json --output candidate.txt
python <技能目录>/scripts/edit_guard.py check --session edit-001 --edits edits.json --candidate candidate.txt
```

工具按冻结基线拼回全文，范围外保持原始 UTF-8 字节。输出必须是新文件；不覆盖已有稿件或会话快照。读取 `candidate.txt`，对照要求检查范围内的语义及跨段衔接，通过后以该文件作为本次完整成品。不要检查文件 A 后又自由重写文件 B 作为交付；交付附件时用已检查文件，粘贴正文时直接读取其内容。

检查失败先查错误原因，修正相关输入并重跑。不能无视非零退出码，也不能删除检查失败证据再称“一次通过”。基线或要求已有更新时重新核对权威来源，用新会话准备，不修改旧清单的哈希来让旧稿过关。

## 3. 分清程序证据与语义判断

- `scope_preserved`：候选稿与允许替换拼出的全文一致，范围外没有改写；它不证明允许范围本身选得正确。
- `semantic_check: not_evaluated`：程序没有评判情绪、逻辑、事实或质量。由 AI 将具体要求对照实际句子；确实不能兼顾时才说明取舍，不把程序通过当作品合格。
- 新鲜度检查只覆盖四个声明输入及其快照；`source` 是来源说明，不会自动读取来源所指的其他文件。上游规则改了但要求 JSON 没更新，程序无法发现，所以开工前核对权威正文不能省。
- 哈希用于发现输入漂移、误改和旧会话复用，不是对恶意本机修改的安全认证。程序不调用模型、不联网、不自动修改经验。

日常交付简短说明实际结果即可，例如“已只缩短反应段，其他原文保持；情绪仍保留认出字迹、眼红和攥纸条”。不能声称强制宿主每轮调用、所有聊天加载或员工自动更新。真正出现的新反馈仍按原有经验维护规则处理，不把每个会话快照都升级为长期经验。

## 设计依据

这里采用“模型判断语义，脚本执行确定性操作”的分工，参考 [OpenAI Agents SDK 的技能实践](https://developers.openai.com/blog/skills-agents-sdk)。该资料支持这种分工，不证明本技能已经降低员工返工率；本项目的效果仍以自己的真实案例和实际执行记录核验。
